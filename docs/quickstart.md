# 落地清单（从零到跑起来）

> 这一页回答一个问题：**我要做什么，才能在我自己的环境里把它跑起来？**

## 第 0 步 · 先跑 demo（5 分钟）

照 `examples/minimal/README.md` 跑一遍。
★ **先看到消息落档，再谈落地** —— 不然你在改一个没验证过的东西。

## 第 1 步 · 确定三件事

```
① 有哪些 agent？        → AGENTS 数组
② 谁能派给谁？          → HANDOFF_EDGES（★ 显式、可枚举）
③ 怎么唤起一个 agent？  → 你的执行命令（claude -p / codex exec / …）
```

★ **第 ② 条最容易被忽略，但它最重要** ——
**"谁可以派给谁"是个权力问题，必须显式写下来，不能靠约定。**

## 第 2 步 · 把薄壳接到你的执行器

薄壳的最后一步是"执行命令"。把 demo 里的 `echo` 换成真实的：

```bash
dispatch --from planner --to coder --thread "${TASK}" -- \
  claude -p "$(cat "${PROMPT_FILE}")"
```

★ **注意：注入的「开工须知」应当拼在 prompt 里**，而不是环境变量 ——
因为**被派方要能"读到"它，不是"继承"它**。

## 第 3 步 · 接心跳

被派方要**在执行期间持续写心跳**，薄壳才能"挡在忙的"。

```
在派活开始时:  setHeartbeat(agent, 'dispatch/working', { handoff })
执行过程中:    同上（定期刷新，避免被当成僵死）
在结束时:      setHeartbeat(agent, 'dispatch/end', { exit })
```

★★ **关键约定：只有 `event` 以 `dispatch/` 开头的，才算"真有一个派活在跑"。**

为什么？因为**同一个心跳文件往往双方都会写**
（harness 写会话状态、薄壳写派活状态）——
不区分就会互相覆盖，导致**误判"没在跑"**。

## 第 4 步 · 接 cron（哨兵）

```cron
0 * * * *  cd /path/to/repo && node src/sentinel.mjs >> sentinel.log 2>&1
```

★ **哨兵只报警，不处置**（见 README 设计判断 ③）。
**它写进 `inbox/`，等人来看** —— 不杀任何进程。

## 第 5 步 · 决定归档策略

- **小规模**：`close` 后手动 `mv` 到 `archive/`；
- **中等规模**：加个 `ledger` 日结，每天早上把昨天的已关线程归档；
- ★ **别自动删** —— 归档的目的是"还能查到"，删了就查不到了。

## 常见落地错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 心跳只有 detach 路径写 | 同步派活时读到**上次**的旧心跳 ⇒ 误判"没在跑" | ★ **所有路径都写** |
| `pgrep` 只匹配一种命令形式 | `claude -p` 匹配不到 `claude --resume <id> -p` ⇒ 误报"没在跑" | ★ **覆盖所有调用形式** |
| 变量后紧跟中文标点 | `$FROM：` 被当成变量名 ⇒ `unbound variable` | ★ **一律写 `${FROM}`** |
| 哨兵"顺手"杀掉可疑进程 | **误杀不可逆** | ★ **只报警** |

★★★ **这几条有一个共同的形状**：**"两条路径只改了一条"**。
所以**加任何机制前，先问一句：这个机制有几条路径？**
