# 踩过的坑

> 三个真实事故。每个都写清 **现象 / 怎么发现的 / 根因 / 修法 / 留下来的一句话**。
>
> 这份文档比代码值钱 —— 代码你抄走就能跑，坑你得自己踩一遍才长记性。
> 所以我先替你踩了。

---

## 坑一：看板说它"离线"，其实它在跑

**现象**：看板里 `kimi-code` 的状态字段是 `offline`（渲染成「挂机」）。我据此判断"它闲着呢"。

> 这里不配截图，因为**截图是"现在"的状态，不是"当时"的** —— 图文一混，读者会以为看板一直长那样。
> 想复现这种不一致，最省事的办法是下面那两条命令，自己撞一次。

**实际**：它正在跑，turn 8 / step 33，文件 1 分钟前还在写。

**怎么发现的**（两条独立证据，都对上了才算）：

```bash
# ① 进程还在，CPU 不低
ps aux | grep -i kimi | grep -v grep

# ② 会话日志最后一行的 mtime 是刚刚
stat -f "%Sm" ~/.kimi-code/sessions/*/*/agents/main/wire.jsonl
```

**根因**：状态是 **agent 自己上报（push）** 的。

我们的薄壳（`dispatch.sh`）会在派活时"代写"一份状态文件 —— 但它只代写**经它派出去**的活。
**agent 自己开的会话，它不报** ⇒ 看板看不见。

> 看板没错，但它有盲区。**而我拿看板当了判据。**

**修法**：方向换掉 —— **从"等上报"改成"从日志推"（pull）**。
读 transcript 文件的 offset，而不是信任一份可能过期的状态 JSON。

**留下的一句话**：

> **「看起来停了」≠「真的停了」。状态必须能从事实（日志/进程）重算，不能只靠被观测者自述。**

## 坑二：iCloud 把消息目录读卡死

**现象**：每小时一次的熔断扫描 cron 一直报「执行失败 · 原因: 超时」。手动跑也卡 60 秒以上。

**排查过程**（这里走了弯路，值得记）：

1. 先怀疑脚本 —— **拿 2 条消息的小集合跑同一份代码：0.13 秒** ⇒ 逻辑没问题
2. 再怀疑网络/推送 —— 加 `--quiet` 跳过推送，**照样卡** ⇒ 不是它
3. 最后怀疑文件系统：

```bash
ls -lO <消息目录> | grep -c dataless     # → 288
```

**288 / 343 个文件被 iCloud 云化成占位符**（`compressed,dataless`）。
本地只剩壳，读一个就要从云端拉一次。而扫描逻辑**每次都要读全部**（为了判断"线程关没关"）。

**一个骗人的数字**：

```bash
du -sh <云化目录>     # → 20K
```

看着像"文件没了"。实际 2.3 G 都在云上，`du` 只算本地的壳。

**修法**：把目录搬到**不在同步范围**的位置，再软链回来。

```bash
cp -R <同步区>/mailbox/archive ~/.agent-archives/mailbox-archive
rm -rf <同步区>/mailbox/archive
ln -s ~/.agent-archives/mailbox-archive <同步区>/mailbox/archive
```

搬完：**60 秒+ → 0.17 秒**。

**留下的一句话**：

> **同步盘里的文件，可能只有"壳"在本地。凡是要被程序批量读的目录，别放在同步区里。**
>
> 顺带：**`du` 在这种目录上会骗你。**

## 坑三：`-C` 被当成了任务正文

**现象**：

```
Error: File name too long (os error 63)
```

一个"文件名太长"的错误，出现在完全没碰文件的地方。

**根因**：薄壳会给被派活的 agent 注入一段「开工须知」（约 1300 字）。
它的注入逻辑是：**找到命令里的可执行位置，跳过所有以 `-` 开头的参数，把第一段不是 `-` 开头的东西当作 prompt 前置。**

而我们的命令长这样：

```bash
codex exec -C /tmp --skip-git-repo-check "任务正文"
#          ↑↑ 指向目录
```

- `-C` 以 `-` 开头 → 跳过 ✓
- **`/tmp` 不以 `-` 开头 → 被当成 prompt** ✗

于是 1300 字的开工须知被拼到了 `/tmp` 前面，codex 试图把一个 1300 字的字符串当**目录名**用 ⇒ `File name too long`。

**修法**：不传 `-C`，改成**先 `cd` 过去**再调。

**留下的一句话**：

> **给别人的命令行做"参数感知"的文本注入，迟早踩到「这个参数有值」。**
>
> 更稳的做法：**别猜参数结构**。用 stdin、用环境变量、或者让对方自己 `cd`。

## 一条贯穿三个坑的规律

三个坑的形状是同一个：**我信了一个"看起来对"的观测，而不是可重算的事实。**

| 坑 | 我信的 | 真的 |
|---|---|---|
| 一 | 看板显示离线 | 进程在跑、文件在写 |
| 二 | `du` 显示 20K | 2.3 G 在云上 |
| 三 | 报错说"文件名太长" | 是目录参数被吃掉了 |

所以这个项目里那些看起来"啰嗦"的设计，其实都是被这三个坑逼出来的：

- **先落档再执行** —— 因为"没留痕的执行"事后无法复查
- **全追加、零编辑** —— 因为"可改的状态"等于"不可信的状态"
- **状态从事实重算** —— 因为"自述"永远可能过期

## 如果你也想抄

三条纪律，拿走不谢：

1. **handoff 只许沿 pipeline 边** —— 防止 agent 互相乱派；
2. **return 只许向后退** —— 下游无权指挥上游改活；
3. **往返 ≥ 6 次熔断升级给人** —— 防止两个 agent 互相踢皮球。

它们不是想出来的，是**被事故教出来的**。

> 而这大概就是"抛砖引玉"的意思：砖是我们踩坑的形状，玉是你们踩别的坑的形状。
