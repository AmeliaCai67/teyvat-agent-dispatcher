# 架构

## 一、三样东西

```
   ① 薄壳（dispatch）        ② 消息目录（leylines）        ③ 哨兵（cron）
   ─────────────────         ──────────────────────        ──────────────
   所有派活的唯一入口         一条消息 = 一个 .md 文件        每小时扫一遍
   落档 + 挡忙 + 注入         人类可读，grep 可查             发现异常写进 inbox
```

**三者不共享内存、不依赖服务** —— 只靠**文件系统**通信。
⇒ 没有守护进程要维护，没有数据库要备份，**停掉任何一个都不影响另两个。**

## 二、一次派活的完整时序

```
发起方              薄壳                  被派方                地脉目录
  │                  │                      │                     │
  │─ dispatch ──────>│                      │                     │
  │                  │─ ① 查未关闭线程 ─────────────────────────> │
  │                  │<─ N 条 ──────────────────────────────────  │
  │<─ 提醒（软）─────│                      │                     │
  │                  │─ ② 查心跳 ──────────>│                     │
  │                  │<─ busy/idle ─────────│                     │
  │<─ 忙则拒绝 ──────│                      │                     │
  │                  │─ ③ handoff 落档 ────────────────────────> │
  │                  │   ★ 失败 ⇒ 到此为止，不执行               │
  │                  │─ ④ 注入开工须知 ────>│                     │
  │                  │─ 执行命令 ──────────>│                     │
  │                  │<─ 全量输出 ──────────│                     │
  │                  │   落 dispatch-logs/<handoff-id>.log ────> │
  │                  │─ ⑤ report 落档 ─────────────────────────> │
  │<─ 结果 ──────────│                      │                     │
```

★ ③ 和 ⑤ 是**同一件事的两端**：report 的 `ref` 指回 handoff 的 `id` ——
**一次派活因此可复盘：谁派的、派了什么、结果如何，一条链。**

## 三、数据布局

```
leylines/
├── mailbox/
│   ├── 20261013-1415-001-xxx.md     未关闭的线程
│   └── archive/                     已关闭线程（工具【照读】—— 归档是搬家，不是删除）
├── dispatch-logs/
│   └── 20261013-1415-001.log        每次派活的全量输出（可能很大）
├── inbox-<owner>/                   哨兵写给人看的升级文件
└── ledger.md                        日报
```

## 四、三种"停"的区分（★ 这个区分很重要）

```
① 真的停了    —— 进程没了
② 看起来停了  —— 进程还在，但很久没输出          ← ★ 最容易误判的一种
③ 其实在忙    —— 在跑一个很慢的工具（比如 ssh 轮询 9 分钟一次）
```

★ 本项目的所有机制**只处理 ①，对 ② 只报警不处置** ——
因为**把 ③ 误判成 ② 的代价，比漏报一次大得多**（误杀一个正在跑的 agent 不可逆）。

**判据的选择**：能确定的时候用强判据（进程是否存活）；
不能确定的时候**用弱判据 + 只提醒**（"已运行 N 秒未完成，请人工确认"）。

## 五、心跳（heartbeat）

被派方会持续写一个**共享的状态文件**（每个 agent 一个）：

```
{"event": "dispatch/working", "pid": 1234, "ts": "..."}
```

★ **关键约定：只有 `event` 以 `dispatch/` 开头的，才代表"真的有一个派活在跑"。**

因为同一个文件**双方都会写**（插件写会话状态，薄壳写派活状态）——
**不区分就会互相覆盖，导致误判"没在跑"。**

## 六、为什么没有数据库

| 需求 | 文件系统的答案 |
|---|---|
| 存消息 | 一个 `.md` 文件 |
| 查线程 | `grep -l 'thread: xxx' mailbox/*.md` |
| 归档 | `mv` 到 `archive/` |
| 给人看 | 扔进 Obsidian |
| 备份 | `git` |
| 出问题 | `cat` 那个文件 |

★ **人类可读和机器可读不必二选一** —— 这是选文件而不是数据库的**唯一**理由，
而它足够充分。
